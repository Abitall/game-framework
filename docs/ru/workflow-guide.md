# OpenCode Game Studios — полное руководство по процессу

> **Как пройти путь от нуля до выпущенной игры с архитектурой агентов.**
>
> Руководство проводит через все фазы разработки: система из 52 агентов,
> 86 команд и 3 TypeScript-плагина. Предполагается, что OpenCode установлен,
> а работа идёт из корня проекта.
>
> В процессе семь фаз. У каждой есть формальный гейт (`/gate-check`), который
> нужно пройти, прежде чем двигаться дальше. Эталонная последовательность фаз
> описана в `docs/framework/workflow-catalog.yaml` и читается командой `/help`.

> Русская копия `WORKFLOW-GUIDE.md`. Оригинал — источник истины.

## Быстрый старт

### Что нужно

- **OpenCode** установлен и работает
- **Git** с Git Bash (Windows) или обычный терминал (macOS/Linux)
- **Node.js 18+** для установщика модулей и git-хуков
- Никаких `jq` и Python — хуки написаны на TypeScript

### Шаг 1. Клонировать и открыть

```bash
git clone <repo-url> my-game
cd my-game
npm install
```

### Шаг 2. Запустить `/start`

Если это первая сессия:

```
/start
```

Онбординг спросит, где вы находитесь, и направит в нужную фазу:

- **Путь A** — идеи нет: ведёт в `/concept-brainstorm`
- **Путь B** — идея расплывчата: `/concept-brainstorm` с затравкой
- **Путь C** — концепт ясен: `/setup-engine`, `/prototype`, затем `/map-systems`
- **Путь D1** — проект есть, артефактов мало: обычный поток
- **Путь D2** — проект есть, GDD и ADR уже есть: `/project-stage-detect`,
  затем `/adopt` для миграции
- **Путь E** — несколько идей: `/explore` для быстрых прототипов, затем
  `/gate-check workflow-selection`, чтобы выбрать Hybrid или полный процесс

### Шаг 3. Проверить, что плагины работают

Начните новую сессию. Плагин `ccgs-hooks` печатает блок контекста и статус
проверок:

```
=== OpenCode Game Studios -- Session Context ===
Branch: main
Recent commits:
  abc1234 Initial commit
===================================
```

Если блок есть — всё работает. Если нет, проверьте, что `opencode.json`
перечисляет три плагина в разделе `plugins`.

### Шаг 4. Спрашивать помощь в любой момент

```
/help
```

Читает текущую фазу из `production/PIPELINE.md`, смотрит, какие артефакты есть,
и говорит, что делать дальше. Отличает обязательные шаги от необязательных.

### Шаг 5. Структура каталогов

Каталоги создаются по мере надобности. Система ожидает такую раскладку:

```
src/                  # код игры
  core/               # движковый код
  gameplay/           # геймплейные системы
  ai/                 # ИИ
  networking/         # сетевой код
  ui/                 # интерфейс
  tools/              # инструменты разработчика
assets/               # ассеты
  art/                # спрайты, модели, текстуры
  audio/              # музыка, звуки
  vfx/                # эффекты
  shaders/            # шейдеры
  data/               # JSON-конфиги и данные баланса
design/               # документы дизайна
  gdd/                # GDD
  narrative/          # сюжет, лор, диалоги
  levels/             # документы уровней
  balance/            # данные и отчёты баланса
  ux/                 # спецификации UX
docs/                 # техническая документация
  architecture/       # ADR
  api/                # описание API
  postmortems/        # постмортемы
tests/                # тесты
prototypes/           # выбрасываемые прототипы
  explore/            # прототипы до выбора процесса
  archive/            # архив после выбора
production/           # спринты, вехи, релизы
  sprints/
  milestones/
  releases/
  epics/              # эпики и стори
  playtests/          # отчёты плейтестов
  session-state/      # состояние сессии (в git не попадает)
  session-logs/       # журнал сессии (в git не попадает)
```

> **Совет:** не нужно всё сразу. Создавайте каталоги по мере достижения фазы.
> Важно соблюдать раскладку, когда создаёте: **система правил** применяет
> стандарты по путям. Код в `src/gameplay/` получает геймплейные правила,
> код в `src/ai/` — правила для ИИ, и так далее.

## Фаза 1: Концепт

### Что происходит

Вы переходите от «идеи нет» или «идея расплывчата» к структурированному
документу концепта со столпами и путём игрока. Здесь вы решаете, **что** вы
делаете и **зачем**.

### Конвейер фазы 1

```
/concept-brainstorm  -->  game-concept.md  -->  /design-review  -->  /setup-engine
     |                                        |                    |
     v                                        v                    v
  10 концептов    документ со            проверка            движок закреплён
  разбор MDA      столпами, MDA,         концепта            в technical-preferences.md
  мотивация       основным циклом,                                |
  игроков         УТП                                              v
                                                               /prototype
                                                                   |
                                                                   v
                                                   одна механика, сыгранная
                                                   руками, сегодня
                                                                   |
                                                                   v
                                                            /map-systems
                                                                   |
                                                                   v
                                                       systems-index.md
                                                       (только ядро: не больше пяти,
                                                        остальное — бэклог)
```

### Шаг 1.1. Брейншторм через `/concept-brainstorm`

Точка входа:

```
/concept-brainstorm
```

Или с подсказкой жанра:

```
/concept-brainstorm roguelike deckbuilder
```

**Что происходит:** скилл ведёт через совместный процесс из шести шагов по
студийным методикам:

1. Спрашивает про интересы, темы и ограничения
2. Генерирует 10 затравок с разбором MDA (механики, динамика, эстетика)
3. Вы выбираете 2-3 для глубокого разбора
4. Делает карту мотивации игроков и целевой аудитории
5. Вы выбираете победивший концепт
6. Оформляет его в `design/gdd/game-concept.md`

Документ концепта включает:

- питч одним предложением
- основную фантазию (кем игрок себя воображает)
- разбор MDA
- целевую аудиторию (типы Бартла, демография)
- схему основного цикла
- уникальное торговое предложение
- похожие игры и отличие от них
- столпы игры (3-5 неизменных ценностей дизайна)
- анти-столпы (чего игра намеренно избегает)

### Шаг 1.2. Проверить концепт (необязательно, но полезно)

```
/design-review design/gdd/game-concept.md
```

Проверяет структуру и полноту до того, как вы пойдёте дальше.

### Шаг 1.3. Выбрать движок

```
/setup-engine
```

Или сразу с движком:

```
/setup-engine godot 4.7
```

**Что делает `/setup-engine`:**

- заполняет `docs/framework/technical-preferences.md` соглашениями об именах,
  бюджетами производительности и настройками движка
- определяет пробелы в знаниях (версия движка новее обучающих данных модели)
  и советует сверяться с `docs/engine-reference/`
- создаёт справочники с закреплённой версией в `docs/engine-reference/`

**Почему это важно:** после выбора движка система знает, каких специалистов
использовать. Выбрали Godot — ваши эксперты `godot-specialist`,
`godot-gdscript-specialist` и `godot-shader-specialist`.

### Шаг 1.4. Сделать одну механику играбельной

Прежде чем писать хоть один документ дизайна, сделайте основную механику
играбельной руками:

```
/prototype
```

Одна механика, одна гипотеза, несколько часов. Живёт в `prototypes/` или прямо в
скелете, который идёт с шаблоном, и играете в неё вы сами.

**Почему до документов:** дизайн про механику, которую никто не играл, нельзя
опровергнуть. Он накапливается, и каждая следующая правка заводит новое
противоречие. Прототип отвечает на один вопрос — *стоит ли это строить* — за
несколько часов и без документов.

Запишите вывод одной страницей (`/playtest-report`). Эта страница — первый вход
для индекса систем.

### Шаг 1.5. Разложить ядро на системы

Теперь перечислите системы и сразу сократите список:

```
/map-systems
```

Создаёт `design/gdd/systems-index.md` — главный документ учёта:

- активных систем не больше **пяти**; остальное уходит в бэклог или в «вырезано»
- для каждой активной системы сказано, что игрок делает руками и как проверить
  её за десять минут
- строит зависимости между активными системами
- назначает уровни приоритета (MVP, вертикальный срез, альфа, полная версия)
- определяет порядок проектирования (фундамент → ядро → фичи → подача → полировка)

Потолок — не скромность, а единственное, что держит документы проверяемыми:
каждая система, спроектированная до того, как её можно сыграть, умножает число
способов, которыми документы могут разойтись, и ни одно из этих расхождений
нельзя решить игрой. `node tools/systems-count.mjs` падает, когда активных
систем больше пяти.

### Гейт фазы 1

```
/gate-check concept
```

**Что нужно для прохождения:**

- движок настроен в `technical-preferences.md`
- `design/gdd/game-concept.md` существует и содержит столпы
- скелет собирается и проходит тесты: `npm run check:slice`
- **вы сыграли одну механику руками** и сказали, что её стоит строить
- `design/gdd/systems-index.md` существует, активных систем не больше пяти

**Вердикт:** PASS / CONCERNS / FAIL. CONCERNS пропускает с признанными рисками.
FAIL блокирует движение.

## Фаза 2: Проектирование систем

### Что происходит

Вы пишете документы только для систем ядра — их не больше пяти — и каждую
систему играете до того, как проектируется следующая. Это не «сначала весь
дизайн, потом код»: система описывается, встраивается в скелет, играется вами,
и только потом следующая получает документ.

Конфликты значений между документами ищет `/consistency-check` (один владелец,
один скан по реестру), противоречия в прозе и теорию дизайна — `/review-all-gdds`.
Перечитывать всё, чтобы подтвердить вердикт, который уже лежит в отчёте, никто
не обязан.

### Конвейер фазы 2

```
/map-systems next  -->  /design-system  -->  /design-review
       |                     |                     |
       v                     v                     v
  следующая система     написание GDD        проверка 8
  из systems-index      по разделам          обязательных разделов
                        (пошаговая запись)    APPROVED/NEEDS REVISION
                                                       |
                                                       v
                                            встроить в скелет,
                                            сыграть руками (вы)
                                                       |
                                                       v
                                            следующая система или стоп
       |
       |  (после последней системы ядра)
       v
/consistency-check  -->  /review-all-gdds
                              |
                              v
                конфликты значений, проза, теория дизайна
                PASS / CONCERNS / FAIL
```

### Шаг 2.1. Написать GDD систем

Проектируйте системы в порядке зависимостей:

```
/map-systems next
```

Выбирает систему с наивысшим приоритетом и передаёт в `/design-system`, который
ведёт по разделам. Можно и напрямую:

```
/design-system combat-system
```

**Что делает `/design-system`:**

1. Читает концепт, индекс систем и связанные GDD
2. Проводит предварительную проверку технической осуществимости
3. Проводит через каждый из 8 обязательных разделов по одному
4. Каждый раздел идёт по схеме: контекст → вопросы → варианты → решение →
   черновик → одобрение → запись
5. Каждый раздел пишется в файл сразу после одобрения (переживает падения)
6. Сообщает о конфликтах с уже утверждёнными GDD
7. Маршрутизирует к специалистам по теме (`systems-designer` для математики,
   `economy-designer` для экономики, `narrative-director` для сюжетных систем)

**8 обязательных разделов GDD:**

| # | Раздел | Что внутри |
|---|--------|-----------|
| 1 | **Обзор** | Система одним абзацем |
| 2 | **Фантазия игрока** | Что игрок воображает и чувствует |
| 3 | **Подробные правила** | Однозначные механические правила |
| 4 | **Формулы** | Все расчёты с переменными и диапазонами |
| 5 | **Краевые случаи** | Что происходит в странных ситуациях — явно решено |
| 6 | **Зависимости** | Связи с другими системами (в обе стороны) |
| 7 | **Ручки настройки** | Что дизайнер может менять и в каких пределах |
| 8 | **Критерии приёмки** | Как проверить, что работает. Конкретно и измеримо |

Плюс раздел **ощущения**: референс ощущения, отзывчивость ввода (мс/кадры),
цели по анимации (старт/активная фаза/восстановление), моменты удара, профиль
веса.

### Шаг 2.2. Проверить каждый GDD

Перед следующей системой:

```
/design-review design/gdd/combat-system.md
```

Проверяет все 8 разделов на полноту, ясность формул, решённые краевые случаи,
двусторонние зависимости и проверяемые критерии приёмки.

**Вердикт:** APPROVED / NEEDS REVISION / MAJOR REVISION. Дальше идут только
APPROVED.

### Шаг 2.3. Мелкие изменения без полного GDD

Для тюнинга, небольших дополнений и правок:

```
/quick-design "добавить 10% бонуса урона за атаку во фланг"
```

Создаёт лёгкую спецификацию в `design/quick-specs/` вместо полного GDD.

### Шаг 2.4. Сквозная проверка GDD

Когда все GDD систем MVP утверждены по отдельности:

```
/review-all-gdds
```

Читает все GDD сразу и делает два прохода.

**Проход 1 — согласованность:**
- двусторонность зависимостей (A ссылается на B — ссылается ли B на A?)
- противоречия правил между системами
- устаревшие ссылки на переименованные или удалённые системы
- конфликты владения (две системы претендуют на одну ответственность)
- совместимость диапазонов формул (выход A помещается во вход B?)
- сверка критериев приёмки

**Проход 2 — теория дизайна:**
- конкурирующие циклы прогрессии (две системы борются за одну награду?)
- когнитивная нагрузка (больше 4 активных систем одновременно?)
- доминирующие стратегии (один подход обесценивает остальные?)
- экономические циклы (источники и стоки сбалансированы?)
- согласованность кривой сложности между системами
- соответствие столпам и нарушения анти-столпов
- целостность фантазии игрока

**Выход:** `design/gdd/gdd-cross-review-[дата].md` с вердиктом.

### Шаг 2.5. Нарративный дизайн (если нужен)

Если в игре есть сюжет, лор или диалоги:

1. **Мир** — `world-builder`: фракции, история, география, правила мира
2. **Структура сюжета** — `narrative-director`: арки истории и персонажей,
   нарративные точки
3. **Карточки персонажей** — по шаблону `narrative-character-sheet.md`

### Гейт фазы 2

```
/gate-check systems-design
```

**Что нужно для прохождения:**

- все системы MVP в `systems-index.md` имеют `Status: Approved`
- у каждой системы MVP есть проверенный GDD
- существует отчёт сквозной проверки `design/gdd/gdd-cross-review-*.md`
  с вердиктом PASS или CONCERNS (не FAIL)

## Фаза 3: Техническая подготовка

### Что происходит

Вы принимаете ключевые технические решения, фиксируете их как Architecture
Decision Records (ADR), проверяете на ревью и выпускаете манифест контроля —
плоский список правил для программистов. Здесь же закладываются основы UX.

### Конвейер фазы 3

```
/create-architecture  -->  /architecture-decision (×N)  -->  /architecture-review
        |                          |                                   |
        v                          v                                   v
  мастер-документ           ADR на каждое решение          проверка полноты,
  архитектуры по            в docs/architecture/           порядка зависимостей,
  всем системам             adr-*.md                       совместимости с движком
                                                                      |
                                                                      v
                                                         /create-control-manifest
                                                                      |
                                                                      v
                                                         плоские правила для
                                                         программистов
                                                         docs/architecture/
                                                         control-manifest.md
        Также в этой фазе:
        -------------------
        /ux-design  -->  /ux-review
        документ требований доступности
        библиотека паттернов взаимодействия
```

### Шаг 3.1. Мастер-документ архитектуры

```
/create-architecture
```

Создаёт общий документ архитектуры `docs/architecture/architecture.md`:
границы систем, потоки данных, точки интеграции.

### Шаг 3.2. Architecture Decision Records (ADR)

На каждое значимое техническое решение:

```
/architecture-decision "машина состояний против дерева поведения для ИИ NPC"
```

**Что происходит:** скилл ведёт через создание ADR с разделами:
- контекст и движущие силы решения
- все варианты с плюсами, минусами и совместимостью с движком
- выбранный вариант с обоснованием
- последствия (положительные, отрицательные, риски)
- зависимости (от чего зависит, что включает, что блокирует, порядок)
- требования GDD, которые затрагиваются (по TR-ID)

Жизненный цикл ADR: Proposed → Accepted → Superseded/Deprecated.

**Минимум 3 ADR уровня фундамента** требуется до гейта.

**Доработка существующих ADR:** если ADR уже есть из старого проекта:

```
/architecture-decision retrofit docs/architecture/adr-005.md
```

Определяет, каких разделов шаблона не хватает, и добавляет только их, никогда
не перезаписывая существующее.

### Шаг 3.3. Ревью архитектуры

```
/architecture-review
```

Проверяет все ADR вместе:
- топологическая сортировка зависимостей ADR (находит циклы)
- проверка совместимости с движком
- флаги ревизии GDD (какие разделы GDD нужно обновить из-за решений)
- ведение реестра TR-ID (`docs/architecture/tr-registry.yaml`)

### Шаг 3.4. Манифест контроля

```
/create-control-manifest
```

Берёт все принятые ADR и выпускает плоский список правил:

```
docs/architecture/control-manifest.md
```

Внутри: обязательные паттерны, запрещённые паттерны и ограничения по слоям
кода. Стори, созданные позже, встраивают дату версии манифеста, чтобы можно
было обнаружить устаревание.

### Шаг 3.5. Требования доступности

Создайте `design/accessibility-requirements.md` по шаблону. Зафиксируйте уровень
(Basic / Standard / Comprehensive / Exemplary) и заполните матрицу по четырём
осям: зрение, моторика, когнитивная нагрузка, слух.

Документ обязателен в фазе 3, потому что UX-спецификации фазы 4 ссылаются на
этот уровень: это предпосылка дизайна, а не результат UX.

### Гейт фазы 3

```
/gate-check technical-setup
```

**Что нужно для прохождения:**

- существует `docs/architecture/architecture.md`
- есть минимум 3 принятых ADR
- существует отчёт ревью архитектуры
- существует `docs/architecture/control-manifest.md`
- существует `design/accessibility-requirements.md`

## Фаза 4: Пре-продакшн

### Что происходит

Вы создаёте UX-спецификации ключевых экранов, прототипируете рискованные
механики, превращаете дизайн-документы в реализуемые стори, планируете первый
спринт и собираете вертикальный срез, доказывающий, что основной цикл интересен.

### Конвейер фазы 4

```
/ux-design  -->  /prototype*  -->  /create-epics  -->  /create-stories  -->  /sprint-plan
    |                |                  |                   |                       |
    v                v                  v                   v                       v
 UX-спеки       прототипы          эпики в            стори в                 первый спринт
 design/ux/     prototypes/        production/        production/             с приоритетами
                                   epics/*/EPIC.md    epics/*/story-*.md      sprints/sprint-*.md
    |                                                      |
    v                                                      v
 /ux-review                                          /story-readiness
 (проверка спек                                       (проверка каждой стори
  до эпиков)                                           до взятия в работу)
                                                            |
                                                            v
                                                        /dev-story
                                                      (реализация, маршрутизация
                                                       к нужному агенту)
                         |
                         v
                   вертикальный срез
                   (играбельная сборка,
                    3 сессии без подсказок)
```

\* первый прототип был в фазе 1. Здесь прототипируется только то, что в
ядре всё ещё рискованно.

### Шаг 4.1. UX-спецификации ключевых экранов

До написания эпиков создайте UX-спеки, чтобы авторы стори знали, какие экраны
существуют и какие взаимодействия нужно поддержать.

```
/ux-design main-menu
/ux-design core-gameplay-hud
```

Три режима: экран/поток, HUD, паттерны взаимодействия. Результат — в
`design/ux/`. Каждая спека включает: потребность игрока, зоны раскладки,
состояния, карту взаимодействий, требования к данным, события, доступность,
локализацию.

Читает `accessibility-requirements.md` (фаза 3) и настройки ввода из
`technical-preferences.md` — не нужно повторять их для каждого экрана.

> **Совет:** `/design-system` ставит флаг 📌 UX для каждой системы с
> требованиями к интерфейсу. Используйте эти флаги как чек-лист экранов.

**Библиотека паттернов взаимодействия:**

```
/ux-design interaction-patterns
```

Создаёт `design/ux/interaction-patterns.md`: 16 стандартных элементов
управления плюс игровые паттерны (слот инвентаря, иконка способности, полоса
HUD, диалоговое окно) со стандартами анимации и звука.

**Ревью UX:**

```
/ux-review all
```

Проверяет спеки на соответствие GDD и уровню доступности. Вердикт:
APPROVED / NEEDS REVISION / MAJOR REVISION NEEDED.

### Шаг 4.2. Прототип того, что всё ещё рискованно

Первый прототип был в фазе 1, до документов. Этот шаг — для того, что ядро всё
ещё скрывает: механика, в интересе которой нет уверенности; технический подход,
который может не сработать; два варианта дизайна, между которыми нужно
почувствовать разницу.

Когда:
- механика новая, и вы не уверены, что она интересна
- технический подход рискован, и вы не уверены, что он осуществим
- два варианта дизайна выглядят рабочими, и нужно почувствовать разницу

```
/prototype "движение крюком-кошкой с инерцией"
```

**Что происходит:** скилл вместе с вами определяет гипотезу, критерии успеха и
минимальный объём. Агент `prototyper` работает в изолированном git-worktree,
поэтому выбрасываемый код не попадает в `src/`.

**Ключевое правило:** правило `prototype-code` намеренно ослабляет стандарты —
жёсткие значения допустимы, тесты не обязательны, — но README с гипотезой и
выводами обязателен.

### Шаг 4.3. Эпики и стори из артефактов дизайна

```
/create-epics layer: foundation
/create-stories [slug-эпика]   # повторить для каждого эпика
/create-epics layer: core
/create-stories [slug-эпика]   # повторить для каждого эпика ядра
```

`/create-epics` читает GDD, ADR и архитектуру и определяет объём эпика — один
эпик на архитектурный модуль. Затем `/create-stories` разбивает эпик на
реализуемые файлы стори в `production/epics/[slug]/`. Каждая стори содержит:

- ссылки на требования GDD (по TR-ID, не цитатой — чтобы не устаревало)
- ссылки на ADR (только принятые; Proposed даёт `Status: Blocked`)
- дату версии манифеста контроля (для обнаружения устаревания)
- заметки по реализации под движок
- критерии приёмки из GDD

Когда стори есть, `/dev-story [путь]` реализует одну — и сам маршрутизирует к
нужному программисту.

### Шаг 4.4. Проверка стори перед взятием

```
/story-readiness production/stories/combat-damage-calc.md
```

Проверяет полноту дизайна, покрытие архитектурой, ясность объёма, определение
готовности. Вердикт: READY / NEEDS WORK / BLOCKED.

### Шаг 4.5. Оценка трудоёмкости

```
/estimate production/stories/combat-damage-calc.md
```

Даёт оценку с учётом рисков.

### Шаг 4.6. Планирование первого спринта

```
/sprint-plan new
```

**Что происходит:** агент `producer` вместе с вами планирует спринт:
- спрашивает цель спринта и доступное время
- раскладывает цель на «обязательно / желательно / если успеем»
- выявляет риски и блокеры
- создаёт `production/sprints/sprint-01.md`
- заполняет `production/sprint-status.yaml` (машиночитаемый трекер)

### Шаг 4.7. Вертикальный срез (жёсткий гейт)

Перед переходом в продакшн нужно собрать и отыграть вертикальный срез:

- один полный основной цикл, играбельный от начала до конца
- репрезентативное качество (не всё — заглушки)
- отыгран без подсказок минимум в 3 сессиях
- написан отчёт плейтеста (`/playtest-report`)

Это **жёсткий гейт**: `/gate-check` вернёт FAIL, если человек не играл в сборку
без подсказок.

### Гейт фазы 4

```
/gate-check pre-production
```

**Что нужно для прохождения:**

- минимум 1 проверенная UX-спека в `design/ux/`
- ревью UX завершено (APPROVED или NEEDS REVISION с зафиксированными рисками)
- минимум 1 прототип с README
- файлы стори существуют в `production/stories/`
- существует минимум 1 план спринта
- существует минимум 1 отчёт плейтеста (срез отыгран в 3+ сессиях)

## Фаза 5: Продакшн

### Что происходит

Основной производственный цикл. Вы работаете спринтами (обычно 1-2 недели),
реализуете фичи стори за стори, отслеживаете прогресс и закрываете стори через
структурированное ревью завершения. Фаза повторяется, пока игра не станет
содержательно полной.

### Конвейер фазы 5 (на спринт)

```
/sprint-plan new  -->  /story-readiness  -->  реализация  -->  /story-done
       |                     |                     |                 |
       v                     v                     v                 v
  спринт создан        стори проверена       код написан      ревью из 8 шагов:
  sprint-status.yaml   вердикт READY         тесты прошли     критерии, отклонения,
  заполнен                                                     статус стори
       |
       |  (повтор для каждой стори до конца спринта)
       v
  /sprint-status  (быстрый снимок на 30 строк в любой момент)
  /scope-check    (если объём растёт)
  /retrospective  (в конце спринта)
```

### Шаг 5.1. Жизненный цикл стори

```
/story-readiness  -->  реализация  -->  /story-done  -->  следующая стори
```

**1. Готовность.** До взятия в работу:

```
/story-readiness production/stories/combat-damage-calc.md
```

Проверяет полноту дизайна, покрытие архитектурой, статус ADR (блокирует, если
ADR ещё Proposed), версию манифеста контроля (предупреждает об устаревании) и
ясность объёма. Вердикт: READY / NEEDS WORK / BLOCKED.

**2. Реализация.** Работа с подходящим агентом:

- `gameplay-programmer` — геймплейные системы
- `engine-programmer` — ядро движка
- `ai-programmer` — поведение ИИ
- `network-programmer` — мультиплеер
- `ui-programmer` — интерфейс
- `tools-programmer` — инструменты разработчика

Все агенты следуют совместному протоколу: читают дизайн-документ, задают
уточняющие вопросы, предлагают архитектурные варианты, получают одобрение и
только потом реализуют.

**3. Завершение.**

```
/story-done production/stories/combat-damage-calc.md
```

Ревью завершения из 8 шагов:
1. Найти и прочитать файл стори
2. Загрузить связанные GDD, ADR и манифест контроля
3. Проверить критерии приёмки (автоматические, ручные, отложенные)
4. Найти отклонения от GDD/ADR (BLOCKING / ADVISORY / OUT OF SCOPE)
5. Предложить код-ревью
6. Сформировать отчёт завершения (COMPLETE / COMPLETE WITH NOTES / BLOCKED)
7. Поставить стори `Status: Complete` с заметками
8. Показать следующую готовую стори

Техдолг, найденный на ревью, записывается в `docs/tech-debt-register.md`.

### Шаг 5.2. Отслеживание спринта

```
/sprint-status
```

Быстрый снимок на 30 строк из `production/sprint-status.yaml`.

Если объём растёт:

```
/scope-check production/sprints/sprint-03.md
```

Сравнивает текущий объём с исходным планом, отмечает рост и предлагает, что
урезать.

### Шаг 5.3. Учёт контента

```
/content-audit
```

Сравнивает заявленный в GDD контент с реализованным. Ловит пробелы рано.

### Шаг 5.4. Распространение изменений дизайна

Когда GDD меняется после создания стори:

```
/propagate-design-change design/gdd/combat-system.md
```

Сравнивает GDD по git, находит затронутые ADR, строит отчёт о влиянии и
проводит через решения: заменить, обновить или оставить.

### Шаг 5.5. Фичи на несколько систем (командные скиллы)

```
/team-combat "лечащая способность с HoT и снятием эффектов"
/team-narrative "контент второго акта"
/team-ui "редизайн экрана инвентаря"
/team-level "уровень лесного подземелья"
/team-audio "проход по боевому звуку"
```

Каждый командный скилл ведёт совместный процесс из шести фаз:
1. **Дизайн** — game-designer спрашивает и предлагает варианты
2. **Архитектура** — lead-programmer предлагает структуру кода
3. **Параллельная реализация** — специалисты работают одновременно
4. **Интеграция** — gameplay-programmer связывает всё
5. **Проверка** — qa-tester сверяет с критериями приёмки
6. **Отчёт** — координатор подводит итог

Оркестрация автоматическая, но **точки решения остаются за вами**.

### Шаг 5.6. Ревью спринта и следующий спринт

```
/retrospective
```

Анализирует план против факта, скорость, блокеры и даёт конкретные улучшения.

Затем:

```
/sprint-plan new
```

### Шаг 5.7. Обзор вех

```
/milestone-review "alpha"
```

Даёт полноту фич, метрики качества, оценку рисков и рекомендацию go/no-go.

### Гейт фазы 5

```
/gate-check production
```

**Что нужно для прохождения:**

- все стори MVP завершены
- плейтесты: 3 сессии, покрывающие нового игрока, середину игры и кривую сложности
- гипотеза об «интересности» подтверждена
- в данных плейтестов нет циклов непонимания

## Фаза 6: Полировка

### Что происходит

Игра функционально полная. Теперь нужно сделать её хорошей: производительность,
баланс, доступность, звук, визуальная полировка, плейтесты.

### Конвейер фазы 6

```
/perf-profile  -->  /balance-check  -->  /asset-audit  -->  /playtest-report (×3)
      |                  |                    |                    |
      v                  v                    v                    v
  профилирование     разбор формул       проверка имён,      покрыть: нового
  CPU/GPU, памяти,   и данных на         форматов, размеров  игрока, середину,
  оптимизация        сломанные кривые                        кривую сложности

  /tech-debt  -->  /team-polish
      |                |
      v                v
  учёт и           согласованный проход:
  приоритизация    производительность + арт +
  долгов           звук + UX + QA
```

### Шаг 6.1. Профилирование

```
/perf-profile
```

Ведёт через структурное профилирование:
- зафиксировать цели (FPS, память, платформа)
- найти узкие места, отсортированные по влиянию
- выдать задачи оптимизации с местами в коде и ожидаемым выигрышем

### Шаг 6.2. Анализ баланса

```
/balance-check assets/data/combat_damage.json
```

Ищет статистические выбросы, сломанные кривые прогрессии, вырожденные стратегии
и перекосы экономики.

### Шаг 6.3. Аудит ассетов

```
/asset-audit
```

Проверяет соглашения об именах, форматы файлов и бюджеты размеров по всем
ассетам.

### Шаг 6.4. Плейтесты (нужно 3 сессии)

```
/playtest-report
```

Структурированные отчёты. Три сессии обязательны, покрывают:
- опыт нового игрока
- системы середины игры
- кривую сложности

### Шаг 6.5. Оценка техдолга

```
/tech-debt
```

Ищет TODO/FIXME/HACK, дублирование кода, слишком сложные функции, отсутствующие
тесты и устаревшие зависимости. Каждый пункт категоризируется и приоритизируется.

### Шаг 6.6. Согласованный проход полировки

```
/team-polish "боевая система"
```

Координирует четырёх специалистов параллельно:
1. Оптимизация производительности (performance-analyst)
2. Визуальная полировка (technical-artist)
3. Звук (sound-designer)
4. Ощущение и «сок» (gameplay-programmer + technical-artist)

Приоритеты задаёте вы; команда выполняет с вашим одобрением на каждом шаге.

### Шаг 6.7. Локализация и доступность

```
/localize src/
```

Ищет жёстко зашитые строки, конкатенацию, ломающую перевод, текст без запаса на
расширение и отсутствующие файлы локалей.

Доступность проверяется против уровня, зафиксированного в документе требований
фазы 3.

### Гейт фазы 6

```
/gate-check polish
```

**Что нужно для прохождения:**

- существует минимум 3 отчёта плейтестов
- согласованный проход полировки завершён (`/team-polish`)
- нет блокирующих проблем производительности
- требования уровня доступности выполнены

### Шаг 7.2. Готовность к запуску (полная проверка)

| **QA** | открытые баги по серьёзности, прохождение регрессии |
| **Нарратив** | полнота диалогов, согласованность лора, опечатки |
| **Локализация** | все строки переведены, нет обрезки, тесты локалей |
| **Доступность** | чек-лист соответствия, тесты вспомогательных функций |
| **Магазин** | метаданные заполнены, скриншоты одобрены, цена задана |
| **Маркетинг** | пресс-кит готов, трейлер, план соцсетей |
| **Сообщество** | черновик патчноутов, FAQ, каналы поддержки |
| **Инфраструктура** | серверы масштабированы, CDN настроен, мониторинг работает |
| **Юридическое** | EULA, политика приватности, COPPA/GDPR |

Каждый пункт получает статус **Go / No-Go**. Для выпуска нужны все Go.

## Сквозные вопросы

Эти темы действуют во всех фазах.

### Режимы ревью директоров

Гейты директоров — это агенты-специалисты, которые проверяют работу на ключевых
шагах. По умолчанию работают на каждой контрольной точке. Интенсивность можно
настроить.

**Задаётся один раз в `/start`.** Сохраняется в `production/review-mode.txt`.

| Режим | Что работает | Кому подходит |
|-------|--------------|---------------|
| `full` | все гейты директоров на каждом шаге | новые проекты, изучение системы |
| `lean` | директора только на переходах фаз (`/gate-check`) | опытные разработчики |
| `solo` | без ревью директоров | геймджемы, прототипы, максимальная скорость |

**Переопределение на один запуск** без смены глобальной настройки:

```
/concept-brainstorm space horror --review full
/architecture-decision --review solo
```

Флаг `--review` работает во всех скиллах с гейтами. Глобальный режим меняется
правкой `production/review-mode.txt` или повторным `/start`.

Полные определения гейтов: `docs/framework/director-gates.md`.

---

### Протокол сотрудничества

Система **совместная, под управлением пользователя**, не автономная.

**Схема:** Вопрос → Варианты → Решение → Черновик → Одобрение

1. Агент задаёт уточняющие вопросы
2. Агент даёт 2-4 варианта с компромиссами и обоснованием
3. Вы решаете
4. Агент готовит черновик по вашему решению
5. Вы смотрите и уточняете
6. Агент спрашивает «Можно записать в [путь]?» до записи

Полный протокол с примерами: `docs/COLLABORATIVE-DESIGN-PRINCIPLE.md`
(русская копия — `docs/ru/collaborative-design-principle.md`).

### Инструмент решений

Агенты используют `question` для структурированного выбора. Схема «объясни →
зафиксируй»: сначала полный разбор в тексте, затем чистый выбор в интерфейсе.
Для дизайнерских, архитектурных и стратегических вопросов. Не для открытых
вопросов-открытий и не для простых подтверждений.

### Координация агентов (три уровня)

```
Уровень 1 (директора):  creative-director, technical-director, producer
                                        |
Уровень 2 (лиды):       game-designer, lead-programmer, art-director,
                        audio-director, narrative-director, qa-lead,
                        release-manager, localization-lead
                                        |
Уровень 3 (специалисты): gameplay-programmer, engine-programmer,
                        ai-programmer, network-programmer, ui-programmer,
                        tools-programmer, systems-designer, level-designer,
                        economy-designer, world-builder, writer,
                        technical-artist, sound-designer, ux-designer,
                        qa-tester, performance-analyst, devops-engineer,
                        analytics-engineer, accessibility-specialist,
                        live-ops-designer, prototyper, security-engineer,
                        community-manager и движковые специалисты
```

**Правила координации:**

- Вертикальное делегирование: директора → лиды → специалисты. Не пропускайте
  уровни в сложных решениях.
- Горизонтальные консультации: агенты одного уровня советуются, но не принимают
  обязательных решений вне своей области.
- Разрешение конфликтов: дизайн — `creative-director`, техника —
  `technical-director`, объём — `producer`.
- Никаких односторонних изменений через границы доменов.

### Автоматические проверки (страховка)

Поведение оригинальных 12 хуков реализовано в плагине `ccgs-hooks`
(`.opencode/plugins/ccgs-hooks.ts`). Таблица ниже — названия поведения, а не
скрипты на диске.

| Поведение | Когда | Что делает |
|-----------|-------|------------|
| `session-start` | начало сессии | показывает ветку, последние коммиты, ищет `active.md` для восстановления |
| `detect-gaps` | начало сессии | находит свежие проекты (нет движка, нет концепта) и предлагает `/start` |
| `pre-compact` | перед сжатием | сохраняет состояние сессии |
| `post-compact` | после сжатия | восстанавливает уведомление |
| `notify` | агент ждёт ввода | уведомление ОС |
| `validate-commit` | перед коммитом | проверяет ссылки на дизайн-документы, валидность JSON, отсутствие жёстких значений |
| `validate-push` | перед пушем | предупреждает о пуше в `main`, `master`, `develop` |
| `validate-assets` | после записи файла | проверяет имена ассетов и валидность JSON |
| `validate-skill-change` | изменён файл скилла | советует `/skill-test` после правки `.framework/library/skills/` |
| `log-agent` | старт агента | пишет вызов в журнал аудита |
| `log-agent-stop` | остановка агента | завершает запись аудита |
| `session-stop` | конец сессии | архивирует состояние и коммитит |

### Устойчивость контекста

**Файл состояния:** `production/session-state/active.md` — живая контрольная
точка. Обновляйте после каждого значимого шага. После любого сбоя (сжатие,
падение, `/clear`) читайте его первым.

**Пошаговая запись:** многорораздельные документы пишутся в файл сразу после
одобрения раздела. Готовые разделы переживают сбои и сжатия, обсуждение
записанного можно смело сжимать.

**Автовосстановление:** поведение `session-start` само находит и показывает
`active.md`. `pre-compact` сохраняет состояние для следующей сессии.

**Трекер спринта:** `production/sprint-status.yaml` — машиночитаемый учёт стори.
Пишется `/sprint-plan` и `/story-done`, читается `/sprint-status`, `/help` и
`/story-done`. Убирает хрупкий разбор markdown.

### Миграция существующего проекта

```
/adopt
```

Или точечно:

```
/adopt gdds
/adopt adrs
/adopt stories
/adopt infra
```

Проверяет существующие артефакты на **формат** (не на наличие), классифицирует
пробелы как BLOCKING/HIGH/MEDIUM/LOW, строит упорядоченный план миграции и
пишет `docs/adoption-plan-[дата].md`. Главный принцип: МИГРАЦИЯ, а не ЗАМЕНА —
существующее никогда не перегенерируется, только дополняется.

Отдельные скиллы поддерживают режим доработки:

```
/design-system retrofit design/gdd/combat-system.md
/architecture-decision retrofit docs/architecture/adr-005.md
```

### Система гейтов

```
/gate-check concept              # концепт → проектирование систем
/gate-check systems-design       # системы → техническая подготовка
/gate-check technical-setup      # техника → пре-продакшн
/gate-check pre-production       # пре-продакшн → продакшн
/gate-check production           # продакшн → полировка
/gate-check polish               # полировка → релиз
```

**Вердикты:**
- **PASS** — требования выполнены, идём дальше
- **CONCERNS** — выполнены с признанными рисками, проходимо
- **FAIL** — не выполнены, движение блокируется с конкретными указаниями

При прохождении обновляется `production/PIPELINE.md` (и только тогда), что
влияет на статусную строку и поведение `/help`.

### Обратная документация

Для кода без дизайн-документов:

```
/reverse-document src/gameplay/combat/
```

Читает существующий код и генерирует документацию в формате GDD.

## Советы, чтобы выжать из системы больше

1. **Сначала дизайн, потом реализация.** Система построена на предположении,
   что дизайн-документ существует до кода. Агенты постоянно ссылаются на GDD.

2. **Используйте командные скиллы для сквозных фич.** Не координируйте четырёх
   агентов вручную — `/team-combat`, `/team-narrative` и другие сделают это сами.

3. **Доверяйте системе правил.** Если правило указало на проблему в коде —
   исправьте. Правила кодируют выстраданный опыт разработки игр.

4. **Сжимайте контекст заранее.** При 65-70% использования контекста делайте
   компакцию или `/clear`. Плагин сохранит прогресс. Не ждите предела.

5. **Берите агента нужного уровня.** Не просите `creative-director` писать
   шейдер. Не просите `qa-tester` принимать дизайн-решения.

6. **Запускайте `/help`, когда не уверены.** Он читает реальное состояние
   проекта и называет один самый важный следующий шаг.

7. **Запускайте `/design-review` до передачи дизайна программистам.** Ловит
   неполные спеки рано, экономит переделки.

8. **Запускайте `/code-review` после каждой крупной фичи.** Ловит архитектурные
   проблемы до того, как они расползутся.

9. **Прототипируйте рискованные механики первыми.** День прототипа экономит
   неделю продакшна на механике, которая не работает.

10. **Держите планы спринтов честными.** Регулярно `/scope-check`. Рост объёма —
    главный убийца инди-игр.

11. **Фиксируйте решения в ADR.** Будущий вы скажет спасибо за записанное
    «почему сделано именно так».

12. **Соблюдайте жизненный цикл стори.** `/story-readiness` до взятия,
    `/story-done` после завершения. Ловит отклонения рано.

13. **Пишите в файлы рано и часто.** Пошаговая запись означает, что решения
    переживают сбои и сжатия. Файл — это память, а не переписка.
