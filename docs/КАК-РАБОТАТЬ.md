# Как работать с фреймворком

Практическая инструкция. Всё, что нужно, чтобы начать новый проект и довести его
до релиза, не заглядывая в исходники фреймворка.

---

## 1. Что это такое

Набор инструментов для OpenCode, который превращает одну сессию в подобие
игровой студии: 52 агента, 86 скиллов, 16 правил, 29 шаблонов документов.

Главное, что нужно понять сразу: **в проекте активно только то, что установлено.**

```
.framework/     библиотека. Лежит всё, агент её не читает.
.opencode/      активное. Только установленные модули. Это и есть контекст.
docs/           документация проекта, шаблоны, решения
design/         GDD и реестр сущностей
src/            код игры
production/     PIPELINE.md, SCOPE.md, спринты, состояние сессии
```

Модуль, который не установлен, не стоит ничего. Поэтому «поставить на всякий
случай» — плохая идея, а «поставить, когда понадобилось» — правильная.

---

## 2. Первый запуск

```bash
npm install          # один раз: ставит tsx, minimatch, git-хуки
opencode
```

В сессии:

| Что ввести | Что произойдёт |
|---|---|
| `/start` | онбординг: спросит, где вы находитесь, и поведёт дальше |
| `/` | список всех команд |
| `/help` | краткая карта возможностей |

`/start` — правильная точка входа для нового проекта. Он спросит про идею,
движок и команду, поставит нужный `engine-*` модуль и создаст скелет каталогов.

## 3. Модули

```bash
node .framework/install.mjs list                 # что есть и что стоит
node .framework/install.mjs info engine-phaser   # состав и триггер установки
node .framework/install.mjs add engine-phaser    # поставить (зависимости сами)
node .framework/install.mjs remove art           # убрать, ваши правки сохранятся
node .framework/install.mjs capture art          # перенести правки в библиотеку
node .framework/install.mjs doctor               # проверить целостность
```

### Что стоит по умолчанию

`core`, `design`, `programming`, `qa`, `release`. Это 17 агентов, 45 скиллов,
10 правил. Для нового проекта этого достаточно.

### Что ставить под задачу

| Ситуация | Модуль |
|---|---|
| проект на Phaser / Unity / Godot / Unreal / SFML3 / Raylib / Bevy | `engine-<движок>` |
| двигать UI мышью вместо просьб агенту | `ui-editor` |
| больше трёх экранов или требования доступности | `ui` |
| второй язык | `localization` |
| внешние ассеты | `art` |
| записанный звук или музыка | `audio` |
| сюжет, лор, диалоги | `narrative` |
| отдельные уровни | `level-design` |
| внешние data-файлы | `data` |
| больше пяти модулей в архитектуре | `architecture` |
| поиск идеи, проверка механики | `prototyping` |
| больше 20 систем, несколько человек | `stories` |
| баги ведутся файлами, нужен профилинг | `qa-advanced` |
| публичный запуск, живые игроки | `release-launch` |
| телеметрия, A/B-тесты | `analytics` |
| команда от трёх человек | `team-orchestration` |

### Правило модулей

Если агенту нужна возможность из неустановленного модуля, он **ставит его сам**,
без вопросов. После установки он обязан сразу отчитаться:

- какой модуль и зачем;
- что добавилось (агенты, скиллы, правила);
- как откатить: `node .framework/install.mjs remove <модуль>`;
- какие файлы установщик пропустил, потому что вы их правили.

Удаление — другое дело: `remove` стирает файлы, поэтому на него агент всегда
спрашивает разрешение.

Ставить «на всякий случай» по-прежнему нельзя: каждый установленный модуль стоит
контекста, поэтому причина должна быть текущей задачей, а не возможной будущей.

Если модуль не понадобился — просто скажите, и агент его уберёт.

## 4. Полный путь проекта

### Фаза 1. Концепт

```
/concept-brainstorm     идея → концепт-документ
```

Выход: `design/gdd/game-concept.md`. Агент задаёт вопросы с вариантами, вы
выбираете. Пишет только после вашего «да».

### Фаза 2. Дизайн систем

```
/map-systems            концепт → список систем и порядок
/design-system <имя>    по одному GDD на систему
/design-review <файл>   проверка GDD на полноту
/review-all-gdds        сквозная проверка всех GDD
```

Выход: `design/gdd/systems-index.md` + по файлу на систему.

### Фаза 3. Архитектура

```
/create-architecture        архитектура целиком
/architecture-decision      одно решение → один ADR
```

Выход: `docs/architecture/architecture.md`, `adr-*.md`.

### Фаза 4. Пре-продакшн

```bash
node .framework/install.mjs add engine-phaser
npm run dev            # порт 5174
npm run play           # порт 5173
npm run publish:play   # только по вашей команде
```

Проверка готовности: `node tools/pipeline.mjs status`.

### Фаза 5. Продакшн

```
/sprint-plan            план спринта
/smoke-check            гейт: билд живой
/test-setup             каркас тестов
/balance-check          разбор чисел, а не ощущений
```

### Фаза 6. Полировка

```
/gauntlet screens       слепое сравнение с эталоном
/perf-profile           профилирование (нужен модуль qa-advanced)
/capture-solution       записать находку
```

### Фаза 7. Релиз

```
/release-checklist      чек-лист
/changelog              журнал изменений
/repo-init              создать репозиторий на GitHub
/repo-sync              коммит и пуш
```

Между фазами: `/gate-check` — вердикт PASS / CONCERNS / FAIL.

## 5. Инструменты

| Команда | Когда |
|---|---|
| `node tools/pipeline.mjs status` | начало сессии: где мы, что открыто |
| `node tools/pipeline.mjs check` | прогнать автоматические гейты |
| `node tools/scope.mjs` | «сколько обещано и сколько есть» |
| `node tools/learn.mjs list` | что накопилось в предложениях |
| `node tools/ab.mjs` / `reveal.mjs` | слепое сравнение кадров |
| `node tools/capture.mjs --url ... --out ...` | снимок экрана для сравнения |
| `node tools/envcheck.mjs` | чего не хватает в окружении |
| `node tools/obsidian.mjs new <тип> "<заголовок>"` | заметка в хранилище Obsidian |
| `node tools/change-model.mjs <model>` | сменить модель у агентов |
| `node tools/check-encoding.mjs` | проверить UTF-8 |
| `node .framework/tools/self-check.mjs` | полная проверка фреймворка |

### Гейты пайплайна

`production/PIPELINE.md` — единственный источник правды о фазе. Гейт нельзя
удалить, только закрыть:

```bash
node tools/pipeline.mjs tick "core loop playable"
node tools/pipeline.mjs skip "accessibility modes" --why "перенесено в бету"
node tools/pipeline.mjs block "store metadata" --why "ждём аккаунт"
```

Если гейт пропал из файла, `status` это заметит. Удаление гейта — самый тихий
способ снизить планку, поэтому он и отслеживается.

### Контракт скоупа

`production/SCOPE.md` — строки вида:

```markdown
- [ ] design documents: 8 — count: fs.readdirSync('design/gdd').filter(f => f.endsWith('.md')).length
```

`node tools/scope.mjs` сравнивает обещанное с фактическим. Если строку удалить,
скрипт сообщит: удаление строки — это снижение планки.

### Журнал решений

```bash
node tools/learn.mjs propose --title "..." --sphere code --what "..." --why "..."
node tools/learn.mjs accept <slug>
```

Принятое ложится в `docs/solutions/<сфера>.md`. Сферы: `code`, `gameplay`, `ui`,
`tests`, `art`, `process`, `tools`.

Записывать стоит, если: задача потребовала больше двух переделок, найден обход
ограничения движка, изменено правило или скилл, приём понадобился во втором месте.

## 6. Два хоста — самая важная часть

| Хост | Порт | Кто пишет | Когда обновляется |
|---|---|---|---|
| Dev | **5174** | агент | постоянно |
| Play | **5173** | никто | только по `/publish-play` |

Агент физически не должен трогать 5173 и `dist-play/`. Это значит, что вы можете
играть, пока он работает.

```bash
npm run dev            # начать работу
npm run play           # открыть себе http://localhost:5173
npm run publish:play   # когда хотите увидеть новое
```

Если «игра не изменилась» — вы на 5173, а снапшот не публиковали.

## 6.1. Заметки в Obsidian

Агент умеет писать в хранилище Obsidian: идеи, концепты, планы, документы,
открытые вопросы. Всё на русском, потому что читаете это только вы.

Плагины не нужны: хранилище — обычная папка с markdown, Obsidian подхватывает
изменения сам.

```bash
node tools/obsidian.mjs vault              # где хранилище и сколько заметок
node tools/obsidian.mjs search "каскад"    # найти, прежде чем создавать
node tools/obsidian.mjs new идея "Название"
node tools/obsidian.mjs check              # битые ссылки, дубли, сироты
node tools/obsidian.mjs index              # пересобрать карты содержания
```

Путь задаётся один раз в `production/obsidian.json`:

```json
{ "vault": "D:\\Obsidian Case\\Game Development" }
```

Правила, которые агент соблюдает:

- одна заметка — одна мысль;
- перед созданием ищет похожие, чтобы не плодить дубли;
- каждая новая заметка ссылается минимум на две существующие;
- ваши заметки без разрешения не правит;
- заголовки без `: / \ ? * " < > |` — Windows такие имена не принимает.

Папки: `00 Входящие`, `10 Идеи`, `20 Концепты`, `30 Планы`, `40 Документы`,
`50 Карты`, `90 Шаблоны`. Шаблоны лежат в хранилище и правятся прямо в Obsidian.

> Спецификации игры (GDD, ADR, стори) остаются в проекте. Хранилище — для
> размышлений, а не для документации.

## 6.2. Выключение после задачи

Если оставляете долгую задачу на ночь, скажите об этом прямо:

> «выключи компьютер, когда закончишь»

Агент делает две вещи:

1. **Ставит флаг** — `node tools/shutdown.mjs arm --reason "ночной прогон"`.
2. **По завершении**: при успехе — `now` (выключение через 90 секунд), при ошибке или блокере — `cancel`, и компьютер остаётся включённым.

Защита от случайного выключения:

- `now` отказывается работать без флага;
- флаг старше 12 часов считается просроченным;
- `cancel` отменяет и запланированное выключение, и флаг;
- отчёт пишется в `production/session-logs/` **до** выключения — иначе вы его не увидите.

Без вашей просьбы агент этот скилл не использует.

## 7. Что делать, когда что-то сломалось

| Симптом | Причина | Решение |
|---|---|---|
| `/` пустой, команд нет | сломаны каталоги `.opencode/*` | `node .framework/install.mjs doctor` |
| агент не видит скилл | модуль не установлен | `node .framework/install.mjs list` |
| «игра не обновилась» | вы на play-хосте | `npm run publish:play` |
| кракозябры в тексте | кодировка | `npm run check:encoding`, затем переписать файл через edit/write |
| агент установил модуль без спроса | так и задумано | откатить: `node .framework/install.mjs remove <модуль>` |
| после `remove` остались файлы | вы их правили | они сохранены намеренно, удалите вручную |
| фреймворк ведёт себя странно | — | `npm run check:self` |
| MCP-сервер горит красным | команда сервера не найдена | `npm run check:env` покажет, какая именно; ненужный сервер выключите в `opencode.json` |

Полная проверка:

```bash
npm test                 # кодировка + плагины + хуки + структура
npm run check:self       # модули, дубликаты, ссылки
```

## 8. Правила, которые агент соблюдает

Их не нужно повторять — они в `AGENTS.md` и `docs/agents/`:

- спрашивает разрешение перед записью файлов;
- задаёт уточняющие вопросы, если задача неоднозначна (кроме «делай сам»);
- ставит модули сам и отчитывается сразу после;
- не удаляет модули без разрешения;
- не трогает плейтест-хост;
- игровые значения — в конфиге, не в коде;
- `src/systems/**` без импортов движка;
- не коммитит без указания.

Если агент ведёт себя иначе — это баг конфигурации, скажите ему об этом.

## 10. Первый проект за десять минут

```bash
npm install
opencode
```

В сессии:

```
/start
```

Ответьте на четыре вопроса: идея, движок, жанр, команда. Дальше агент сам
предложит `engine-*` модуль, создаст каталоги и покажет следующий шаг.

Если идеи нет — `/concept-brainstorm`. Если проект уже есть — `/project-stage-detect`.
